# Runtime, quality and maintenance

This is the maintained operations reference for Total Recall 3.39.1 source. Core owns portable memory/instructions and generic plugin contracts. Auth/secrets, OpenWiki, CRM, mesh and other product capabilities belong to their plugins. Use the main skill's owner table for procedures; this file no longer contains a second obsolete master manual.

Run `startup check --json`, `status --json`, `daemon status`, and relevant plugin status/help. Check configured backend health, authenticated instructions access, selected project/brain, daemon identity, SSSS tooling and freshness separately. A listening port or process is not health. `startup ensure` starts only configured managed stopped services; preserve running/unknown/foreign services. Scope/auth failures are not transport retries.

Before tests/build/release, read the owning test/code-quality skills and actual repository config. Use the sanctioned remote test node, resolved by Total Recall. Run one background checker at a time; honor live locks and never delete another job's lock. Hash/synchronize the exact tested sources, inspect raw completion and exit status, and clean owned test fixtures/jobs. Run full suites for significant changes. Browser mocks do not certify live provider delivery. Never infer publication from a local version bump, a package build or a wrapper exit.

Use the five project files plus source OpenWiki hubs throughout work. Append timestamped actions/failures/verification to the tracker's bottom Action Log. Keep implementation, tests, gates, package, release, deployed source and live evidence distinct. No deferred required work without the user's instruction.

For research queues, discover `research --help`, select project/global scope explicitly, inspect actual unfinished items and cancel only requested items via CLI. Never edit queue storage. For skills, discover `skill --help`, preserve repository ownership, update entrypoints and relevant references, synchronize scaffold, validate links and command ownership, then refresh context. Never copy a personal memory vault into a scaffold/package or between local/cloud brains.

Publication/deployment use the owning push/deploy procedures when authorized. Shared production services require staged health-checked zero-downtime switching and rollback. Do not use a generated restart command as permission to interrupt a serving process.

## Optional developer API

The full server's `/v1/invoke` requires a named auth-owned PAT with a literal `invoke:full` or `invoke:restricted` mode; legacy wildcards and dashboard sessions do not opt in. Full mode requires full grants throughout the issuer chain and intentionally grants trusted host administration, including auth-owned credentials and nested owner execution. Do not describe it as a sandbox or give it to a restricted consumer to bypass a denial.

Restricted `ssss.read` additionally requires `ssss:read` and `brain:server`, uses local server-brain retrieval and spends no provider credits. Restricted `ssss.write` requires `ssss:write` and `brain:server` and creates descriptive facts only through the shared memory owner with generated create-only paths, exact schemas and generator-free local indexing. The same owner supports local `remember fact "content" --confined-fact`. Arbitrary mutation metadata, rule categories, CLI/plugin/composed execution and paid decisions remain unavailable. Capabilities omit denied operations. Fresh role/issuer/expiry/revocation checks, controlled child environment, filesystem permissions, concurrency/time/output bounds and validated SSSS execution audit apply. Mutation errors preserve known commit/index state or report unknown commit state after interruption; effects already committed cannot be rolled back. Provider quotas, broader owner adapters and the complete API/launch journey remain separate acceptance work. Read the shipped `docs/reference/cli-reference.md` developer API contract before migration or execution.

## Uniform dependency updates

Project registration automatically creates and records its stable UUID through the existing identity owner. Malformed/non-object identities are preserved and fail explicitly; provisioning failure must not register an incomplete fallback. `project-id --all` is for legacy reconciliation, not a required step after ordinary registration.

Restricted memory also accepts `project:<uuid>` with the effective auth scope `brain:project-<uuid>` plus its read/write scope. Use existing brain registration/on/off, project-id and auth-key commands. Only registered, enabled, canonical identity-matched brains execute; discovery lists granted usable IDs, never paths. Running work pins and revalidates that binding; removal, disablement or identity/path changes stop continuation. Project-only keys have no implicit server access. Writes retain the closed descriptive fact schema and validated SSSS owner.

Full-mode `decision.run` and `decision.predict` execute the installed owner in bounded children, with auth-owner credential resolution inside the child. Timeout, output overflow, client disconnect and revoked authority terminate local continuation. Decision failure envelopes suppress child diagnostics; credential/provider failures are explicit. Cancellation cannot reverse accepted remote billing. Spending quotas and broader restricted adapters remain separate acceptance work.

Use `total-recall update --all-brains` to plan both SSSS and Total Recall updates across registered brains, installed plugin owners and nested consumers. Add `--apply` to pin the resolved published releases, refresh npm/pnpm locks and verify actual package resolution; `--json` returns per-consumer results and failures. Extra roots use repeatable `--repo` or `TR_SYNC_REPOS`. Every consumer owns a local installation: a shared node_modules link is detached without mutating its former target and restored on failure. Missing versions, unsupported managers, newer previews and verification mismatches fail explicitly. This updates local dependencies; it does not deploy services or merge brains.
