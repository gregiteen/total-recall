# Total Recall Three-Tier Memory Architecture Plan

## Objective

Replace the current monolithic `graph-context.md` eager-loading memory system with a three-tier, filesystem-native memory architecture that works with existing IDE agents such as Antigravity, Cursor, Claude Code, and Codex without requiring control over their internal agent loops.

The system must reduce context rot, prevent silent rule conflicts, force task-relevant memory disclosure through `SKILL.md`, and preserve all durable state as SSSS-compatible Markdown or JSONL artifacts.

## Core Architecture

The new architecture has three tiers:

1. **Tier 1: Hot Memory**
   - Tiny invariant layer in `INSTRUCTIONS.md`, `AGENTS.md`, `.cursorrules`, and `CLAUDE.md`.
   - Strictly under 1,000 tokens.
   - Contains only universal behavioral laws required before any retrieval.
   - Must not contain bulk memory or graph summaries.

2. **Tier 2: Curated Skill Memory**
   - Task-specific memory injected into `.agent/skills/<skill>/SKILL.md`.
   - Each skill receives a bounded generated memory capsule.
   - The agent naturally loads the relevant memory when it loads the skill.

3. **Tier 3: Permanent Vault**
   - Durable source of truth in `.agent/memory-vault/rules/**/*.md`.
   - All nodes use SSSS frontmatter.
   - Derived indexes are generated into `.agent/memory-derived/*.jsonl`.
   - No relational database is required for workspace memory configuration.

## Target Filesystem Layout

```text
.agent/
  memory-vault/
    rules/

  memory-derived/

    skill-routes.jsonl
    conflict-index.jsonl

  memory-inbox/
    pending/
    conflicts/
  skills/
    <skill>/

  rules/
    graph-context.md
    active-context.md
```

## Tier 1: Hot Memory Policy

`INSTRUCTIONS.md` should contain only:

- Text-first before state mutation.
- Skills-first before task execution.
- Never claim a file/tool was read unless actually read.
- Never autonomously steer or modify behavioral memory without approval.
- If a new rule conflicts with old memory, quarantine and ask for explicit resolution.
- Read-only discovery is allowed when needed for factual accuracy.
- Task-specific rules live in the relevant `SKILL.md`.

The old `DISTILLED MEMORY` block should be removed or replaced with a short compatibility stub.

## Tier 2: Skill Memory Routing

The Total Recall compiler should scan all vault rules and route them into skill files using:

- Explicit `routing.explicit_skills` frontmatter.
- Tag overlap.
- TF-IDF similarity between rule text and skill text.
- Priority and confidence weighting.
- Manual override files when needed.

Each `SKILL.md` receives a generated block:

```markdown
<!-- total-recall:memory:start -->
> Generated by Total Recall. Do not edit manually.

- [MUST_NOT] Never run raw `tsc` or `eslint`; use the code-quality scripts. _(memory:rule_no_raw_tsc)_
- [MUST] Read this skill before using its scripts. _(memory:rule_skills_first)_

<!-- total-recall:memory:end -->
```

Capsules should be capped at 5-7 rules per skill to avoid recreating context rot locally.

## Tier 3: Vault Rule Schema

Every durable rule should be represented as SSSS Markdown:

```yaml
---
type: rule
id: rule_text_first
rule_kind: invariant
status: active
modality: must_not
subject: agent
predicate: execute_state_mutating_tool_before_text_response
object: tool_execution
scope:
  repo: ultrachat-ai-powered
  skills: ["*"]
priority: 100
confidence: high
created: 2026-05-11
last_verified: 2026-05-11
provenance:
  - source: user
    ref: session
relationships:
  supersedes: []
  superseded_by: null
  conflicts_with: []
routing:
  explicit_skills: []
  inferred_skills: []
  tags: [rule-zero, tool-execution]
decay:
  half_life_days: 180
  access_count: 0
---
```

## Conflict Resolution Policy

No new rule becomes active immediately if it conflicts with an existing active rule.

Conflict flow:

1. User gives new directive.
2. Total Recall writes it to `.agent/memory-inbox/pending/`.
3. Conflict engine compares it against active vault rules.
4. If no conflict exists, the rule becomes active.
5. If conflict exists, write a conflict file to `.agent/memory-inbox/conflicts/`.
6. Surface the conflict to the user.
7. Wait for explicit human resolution.
8. Only then activate, reject, merge, or supersede.

The current behavior in `steering.mjs` that auto-deletes older conflicting rules must be removed.

## Dream Cycle

The Dream coprocessor runs on cron and file-change events.

Responsibilities:

1. Normalize legacy memory nodes.
2. Deduplicate near-identical rules.
3. Detect stale or low-confidence rules.
4. Detect contradictions.
5. Generate `graph-index.jsonl`.
6. Generate `skill-routes.jsonl`.
7. Inject bounded capsules into skill files.
8. Refresh the hot memory stub only.
9. Append results to `dream-report.jsonl`.

## Migration Plan

### Phase 1: Freeze Monolithic Injection

- Stop expanding `.agent/rules/graph-context.md`.
- Keep it as a compatibility stub.
- Preserve current IDE rule file symlinks.

### Phase 2: Create Vault Structure

- Introduce `.agent/memory-vault/rules/`.
- Migrate `.agent/memory-wiki/**/*.md` into SSSS `type: rule` format.
- Preserve provenance, confidence, sentiment, and evidence.

### Phase 3: Generate Derived Indexes

- Build `.agent/memory-derived/graph-index.jsonl`.
- Build `.agent/memory-derived/skill-routes.jsonl`.
- Do not treat indexes as source of truth.

### Phase 4: Skill Capsule Injection

- Add generated memory blocks to `SKILL.md` files.
- Cap each skill capsule.
- Verify high-risk rules route to the correct skills.

### Phase 5: Conflict Quarantine

- Replace autonomous steer activation with pending rule intake.
- Add conflict files under `.agent/memory-inbox/conflicts/`.
- Require explicit user resolution before activation.

### Phase 6: Shrink Hot Memory

- Reduce `INSTRUCTIONS.md` to universal invariants only.
- Align `AGENTS.md`, `.cursorrules`, `CLAUDE.md`, and Cursor rules.
- Remove bulk graph summaries from always-loaded context.

### Phase 7: Validate Agent Behavior

- Test direct-question turns.
- Test skill-triggered tasks.
- Test conflicting user directives.
- Test stale memory decay.
- Test rule routing accuracy.
- Test no memory is injected globally beyond hot invariants.

## Success Criteria

- `INSTRUCTIONS.md` remains under 1,000 tokens.
- No large generated memory surface is eagerly loaded.
- Every durable memory rule has SSSS frontmatter.
- Every active rule has provenance.
- Conflicting rules are quarantined, not auto-resolved.
- Skill-specific rules appear in relevant `SKILL.md` files.
- Agents are forced to encounter task-relevant memory through normal skill loading.
- Derived JSONL indexes can be deleted and regenerated without data loss.

## Non-Goals

- Do not build a custom IDE agent loop.
- Do not introduce Postgres or external databases for workspace memory.
- Do not rely on agents voluntarily reading a secondary graph file.
- Do not use global context dumps as the primary memory surface.
- Do not auto-delete older rules during conflict resolution.

## Key Decision

The replacement system should treat memory as compile-time filesystem constraints, not runtime prompt stuffing.

The durable source of truth is SSSS Markdown.  
The activation layer is skill-local progressive disclosure.  
The hot prompt is only a safety kernel.
