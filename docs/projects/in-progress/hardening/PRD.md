## 1. Executive Summary

Total Recall is a **sovereign AI system** — a fully private, self-hosted intelligence engine where a local LLM operates as a general-purpose kernel capable of running autonomous agents, executing complex multi-step workflows, writing and running code, and continuously learning from its environment. All of this runs on user-owned infrastructure at **near-zero cost** (~$8–15/month for optional frontier evals at standard DeepSeek V4 Pro rates).

What makes Total Recall fundamentally different is what sits underneath: the proprietary **Structured Semantic Syntax System (SSSS)** — a database-free architecture where all state, memory, logic, agents, and automation are expressed as semantically typed Markdown files in a Virtual File System. **Memory is the core.** Every agent, every workflow, every decision the system makes reads from and writes back to the SSSS Memory Vault. The memory system is what gives the kernel persistent identity, behavioral consistency, and the ability to evolve over time. Everything else — continuous intelligence, Code Mode, voice, tiered frontier routing — is built on top of that foundation.

The kernel is powered by a locally hosted **Gemma 4 26B-A4B** (Mixture-of-Experts) LLM. Because inference runs on the user's own infrastructure, the system enables unlimited background processing — proactively building skills, researching current information, compressing and consolidating memories, executing sandboxed code, and self-optimizing its own workflows autonomously. A user-configured frontier tier (e.g., DeepSeek V4 Pro, ~$8–15/month at standard rates) provides quality gates and evals.

## 2. Core Architecture

### 2.1 The Zero-Parser SSSS Kernel

**Requirement:** The system must not rely on regex parsers, abstract syntax trees, or compiled DSLs to interpret workflow execution steps. The LLM itself is the parser.

**Implementation:**

The core engine is a **Gemma 4 26B-A4B** model running at Q4_K_M quantization via Ollama. Rather than fine-tuning, the system uses **aggressive in-context learning** (see §2.5) — filling the ~32K–48K token context window with SSSS execution examples, behavioral rules, and memory nodes on every call. The memory system IS the training data.

> **Future fine-tuning path:** If in-context learning proves insufficient, a QLoRA fine-tuning dataset of ~15,000 SSSS execution trajectories can be generated by DeepSeek V4 Pro for ~$15–60 total (see §2.5.4).

#### 2.1.1 Gemma 4 26B-A4B — Verified Technical Specifications

| Attribute | Value |
|:---|:---|
| **Architecture** | Mixture of Experts (MoE) |
| **Total Parameters** | ~25.2 billion (commonly cited as 26B) |
| **Active Parameters per Token** | ~3.8 billion (8 of 128 experts routed per token) |
| **Context Window** | 256,000 tokens |
| **Modalities** | Text, Image, Video (native vision encoder) |
| **License** | Apache 2.0 (fully open-source, commercial use) |
| **Release** | April 2, 2026 (Google DeepMind) |
| **Quantization Target** | Q4_K_M (GGUF) |
| **Quantized Weight Size** | ~15–16 GB |
| **Inference Engine** | Ollama (backed by llama.cpp, ARM-optimized) |

**Why MoE matters:** Although ~25.2B parameters must be loaded into RAM, only ~3.8B activate per forward pass (8 of 128 experts selected per token). This delivers reasoning quality comparable to dense 26B models at inference speed approaching a ~4B model — critical for sustained CPU-only throughput on ARM.

#### 2.1.2 SSSS Workflow Interpretation

The kernel natively reads SSSS Markdown files (`type: workflow`) and interprets:

- **Sequential execution** via `## Step N:` headings
- **Conditional branching** via `(Condition: IF expression)` annotations
- **Parallel fanout** via `[Parallel]` step tags
- **Error boundaries** via `[Retry: N, Timeout: Ns, OnError: Step M]` directives
- **Concurrency locks** via `[Lock: resource_name]` mutex annotations
- **Secret injection** via `{{secrets.*}}` mustache-syntax resolution from the global keychain
- **Blackboard state** via VFS scratchpad files (`runs/data_${run_id}.json`)

The in-context learning strategy (§2.5) teaches the model to output **exact tool calls** (Code Mode sandbox invocations, file mutations, assistant spawns) rather than conversational responses when processing workflow files. Few-shot examples curated by the dream cycle provide the behavioral templates.

### 2.2 Continuous Intelligence (Infinite Compute)

**Requirement:** The system must operate 24/7 with autonomous background processing, not limited to user-initiated triggers or batched cron windows.

**Implementation:**

The OS daemon (`dream.mjs`) orchestrates a **priority-driven autonomous task scheduler** that allocates inference budget across competing workloads:

#### 2.2.1 Throughput Budget

At **Q4_K_M quantization** on 4 ARM OCPUs with 24GB RAM, Gemma 4 26B-A4B generates approximately **8–12 tokens/second**. Assuming an average step requires ~500 output tokens:

| Metric | Value |
|:---|:---|
| Time per inference call | ~45–60 seconds |
| Calls per hour | ~60–80 |
| **Calls per day (24h continuous)** | **~1,400–1,900** |

#### 2.2.2 Autonomous Task Scheduler

The daemon is not a simple cron loop — it manages a **priority queue** that dynamically allocates the daily inference budget:

| Priority | Category | Daily Budget | Purpose |
|:---|:---|:---|:---|
| **P0** | User-Facing | Unlimited (preempts all) | Active conversations, explicit requests — always served immediately |
| **P1** | Memory Maintenance | ~200–300 calls | Dream cycle: compression, index rebuilds, schema enforcement, conflict resolution |
| **P2** | Skill Engineering | ~200–400 calls | Building, testing, and improving SSSS skill files autonomously |
| **P3** | Proactive Research | ~200–400 calls | Web search for current information, knowledge refresh, trend monitoring |
| **P4** | Self-Evaluation | ~100–200 calls | Testing own capabilities, running evals, benchmarking accuracy |
| **P5** | Exploration | Remaining budget | Speculative research, low-priority curiosity-driven tasks |

Allocations are not fixed — the scheduler adjusts based on demand. When no P0 tasks exist (user is idle/asleep), background categories get the full budget. The allocation weights are themselves an SSSS rule file that the dream cycle auto-tunes weekly based on which categories produced tasks the user actually used.

**Task queue as an SSSS primitive:** Every autonomous task is a Markdown file in `~/.agent/scheduler/queue/`:

```markdown
---
type: task
priority: 85
category: skill-engineering
target: skills/stripe-expert.md
estimated_calls: 50
deadline: 2026-05-18
created_by: dream-cycle
reason: "User asked about Stripe 3 times this week, no skill exists"
status: pending
progress: 0
---

## Objective
Research Stripe Connect API for marketplace payouts.

## Steps
1. Web search Stripe Connect official docs
2. Write create-connected-account.mjs, test against Stripe test mode
3. Add "Marketplace Payouts" section to stripe-expert.md
4. Run self-eval: can I execute a full payout flow?

## Success Criteria
- [ ] Script tested against Stripe test API
- [ ] Self-eval passes 3/3 payout scenarios
```

**Task generation sources:**

| Source | Trigger | Example |
|:---|:---|:---|
| **Pattern Detection** | User repeatedly asks about a topic with no skill | "User asked about Docker 5x → create docker-expert task" |
| **Staleness Detection** | Memory node `last_refreshed` exceeds threshold | "Tax strategy skill is 90 days old → refresh task" |
| **Workflow Failures** | A workflow step fails | "Stripe webhook threw 422 → research correct format" |
| **Self-Eval Failures** | System tests itself and fails | "Failed 2/5 email scenarios → research SPF/DKIM" |
| **Skill Dependencies** | A skill references another that doesn't exist | "CRM skill needs email-validator → create it" |
| **User Explicit** | User says "learn about X for me" | Direct task creation |

#### 2.2.3 Proactive Intelligence Engine

The system doesn't wait for you to ask — it autonomously builds knowledge in **any domain**, not just development:

**Skill Engineering:** The kernel uses idle cycles to build comprehensive SSSS skill files. Each skill goes through a research → draft → test → refine → expand cycle across multiple inference calls. A single skill can grow to 50K–100K tokens of curated knowledge over days of autonomous work.

**Knowledge Currency:** Web searching compensates for the local model's knowledge cutoff. The system proactively refreshes stale information:
- Monitor regulatory changes relevant to your business
- Track competitor pricing and feature updates
- Refresh technical documentation when APIs change
- Update market data, exchange rates, industry news

**Non-Developer Skill Examples:**

| Domain | What the system builds autonomously |
|:---|:---|
| **Personal Finance** | Tax strategy guides, investment tracking scripts, bank rate comparisons |
| **Health & Wellness** | Evidence-based nutrition summaries, drug interaction databases, fitness protocols |
| **Travel** | Destination guides with visa requirements, transit systems, real-time pricing |
| **Market Research** | Competitive intelligence, industry trend analysis, pricing benchmarks |
| **Legal / Compliance** | Regulatory checklists, policy templates, compliance tracking |
| **Education** | Study guides, concept explanations, practice problem generators |

**Consuming large skills at runtime:** A 100K token skill file doesn't fit in one context window (~48K max). The Progressive Disclosure layer does semantic retrieval — pulling only the relevant sections into context, not the entire file. You get the depth of a massive knowledge base with the speed of a targeted injection.

> **Why this is unique:** API-based systems would spend $50–500/day on this level of background research. Total Recall does it for free. The system literally gets smarter while you sleep.

#### 2.3.1 Web Search & Scraping Implementation

Both tools are **free and self-hosted** — no external API keys required:

| Capability | Implementation | Cost |
|:---|:---|:---|
| **Web Search** | **SearXNG** — open-source, self-hosted metasearch engine running on the same VM. Aggregates results from Google, Bing, DuckDuckGo, and 70+ other engines. No API key, no rate limits, no tracking. | Free |
| **Web Scraping** | Direct HTTP fetch via Node.js `fetch()` + **Mozilla Readability** for content extraction. Converts any web page to clean, structured Markdown. For JS-rendered pages, optional Playwright headless browser. | Free |

SearXNG runs as a lightweight Docker container alongside the kernel (~100MB RAM). The kernel queries it via local HTTP (`http://localhost:8888/search?q=...&format=json`), receives structured JSON results, and can then scrape the top results for full content.

> **Extensibility:** New tools can be added by dropping a tool definition file into `~/.agent/tools/`. The kernel discovers available tools at startup and can use any tool that exposes a standard interface (input schema → output schema). This is how users extend the system without modifying core code.

### 2.4 Code Mode Sandbox (JIT Integrations)

**Requirement:** The system must interact with any external API without pre-built, hardcoded integrations.

**Implementation:**

The system provides a **sandboxed Node.js 22 LTS / Bash execution environment** with:

- **Credential injection** via `{{secrets.*}}` resolution from the encrypted keychain (AES-256-GCM)
- **Network access** for REST/GraphQL/WebSocket calls to arbitrary endpoints
- **File system access** scoped to the VFS (`~/.agent/`) — no host system mutation
- **Execution limits**: 60-second timeout, 512MB memory cap, no `child_process.exec` on host
- **Output capture**: stdout/stderr piped back to the kernel for self-reflection analysis

The kernel can autonomously: read API documentation via web search → generate an integration script → execute it in the sandbox → parse the output → write results to the VFS. No human-authored adapter code required.

### 2.5 Behavioral Adaptation (Memory-Driven In-Context Learning)

**Requirement:** The system must adapt to user-specific behavioral patterns without transmitting data to external servers and without fine-tuning model weights.

**Implementation:**

Because inference is local and free, the system uses **aggressive in-context learning** — filling the context window with behavioral examples, memory nodes, and few-shot demonstrations on every call. The SSSS memory hierarchy IS the adaptation mechanism. No weight changes needed.

#### 2.5.1 Context Window Budget

Gemma 4 26B-A4B supports a theoretical 256K token context window. On 24GB RAM, the practical limit is determined by KV cache memory:

| KV Cache Precision | Usable Context | Notes |
|:---|:---|:---|
| FP16 (default) | ~6,000–12,000 tokens | Conservative, highest quality |
| Q8_0 (recommended) | ~12,000–24,000 tokens | Good quality, 2x capacity |
| **Q4_0 (aggressive)** | **~32,000–48,000 tokens** | **Minimal quality loss, maximum context** |

The system defaults to **Q4_0 KV cache quantization** via llama.cpp flags (`--cache-type-k q4_0 --cache-type-v q4_0`), targeting **~32K–48K usable tokens** per call. This is ~50–80 pages of text.

#### 2.5.2 Context Filling Strategy

Since there are zero per-token costs, the system fills the context window aggressively on every inference call — the opposite of API-cost-conscious architectures:

```
Context Window Layout (~32K–48K tokens):
┌─────────────────────────────────────────────┐
│ 1. Hot Memory (Tier 1)                       │  ~2K–4K tokens
│    - All priority: absolute / modality: must │
│    - Behavioral invariants, identity rules   │
├─────────────────────────────────────────────┤
│ 2. Progressive Disclosure (Tier 2)           │  ~4K–8K tokens
│    - Semantically relevant memory nodes      │
│    - Matched by query similarity to request  │
├─────────────────────────────────────────────┤
│ 3. Few-Shot Examples                         │  ~8K–16K tokens
│    - SSSS workflow execution demonstrations  │
│    - Tool call patterns from past successes  │
│    - Correction examples ("do X not Y")      │
├─────────────────────────────────────────────┤
│ 4. Current Conversation / Task               │  ~8K–16K tokens
│    - The actual user request + history       │
└─────────────────────────────────────────────┘
```

#### 2.5.3 How the Memory System Replaces Fine-Tuning

The dream cycle continuously observes the kernel's behavior and mutates the SSSS memory vault to improve future performance:

| Mechanism | How It Works |
|:---|:---|
| **Pattern Promotion** | When the kernel is corrected >3 times on the same behavior, the dream cycle creates a `category: patterns`, `modality: must` memory node that gets injected into Tier 1 |
| **Few-Shot Curation** | Successful workflow executions are logged; the dream cycle extracts the best examples and writes them to `~/.agent/memory-vault/examples/` for inclusion in the few-shot block |
| **Conflict Resolution** | When contradictory memory nodes are detected, the dream cycle evaluates by `importance` score and marks the loser as `status: superseded` |
| **Context Optimization** | The dream cycle tracks which memory nodes are actually referenced in kernel outputs and deprioritizes unused nodes to free context space |

> **Why this works:** 32K–48K tokens of dense, curated behavioral context is equivalent to thousands of training examples. The kernel sees exactly how to behave, every single call. As the memory vault grows and the dream cycle curates it, the system gets better over time — without touching the model weights.

#### 2.5.4 Future Upgrade Path: LoRA Fine-Tuning

If memory-based adaptation proves insufficient for specific use cases, LoRA fine-tuning remains available as a future upgrade:

- **Cloud-burst training:** Rent GPU hours on RunPod/Lambda (~$1–5/week), train a QLoRA adapter with Unsloth or LlamaFactory, convert to GGUF, load in Ollama via `ADAPTER` directive
- **On-device training:** llama.cpp's `llama-finetune` binary supports LoRA on ARM CPU, but at ~10–50x slower than GPU — viable as an overnight background task
- **Both approaches produce a small adapter file (~50–200MB)** that loads alongside base weights with negligible RAM overhead

### 2.6 Tiered Intelligence Architecture

**Requirement:** The system must provide frontier-grade intelligence for high-stakes tasks while maintaining zero-cost 24/7 operation.

**Implementation:**

The memory vault is sovereign and model-agnostic. The intelligence that reads it is pluggable — bring your own API key:

| Tier | Default | Role | Cost |
|:---|:---|:---|:---|
| **Local Workhorse** | Gemma 4 26B-A4B | 24/7 background processing: skill building, dream cycle, memory maintenance, research, user conversations | Free |
| **Frontier Judge** | User's choice (any OpenAI-compatible API) | Evals, quality gates, complex reasoning fallback, skill validation | Varies (DeepSeek V4 Pro: ~$8–15/mo at standard rates) |

The frontier tier accepts **any OpenAI-compatible API endpoint**. Users configure their preferred provider and API key in `~/.agent/config/frontier.yml`. The system ships with DeepSeek V4 Pro as a recommended default due to its cost efficiency. Pricing is provider-dependent:

| Tier | Input (per 1M tokens) | Output (per 1M tokens) | Notes |
|:---|:---|:---|:---|
| **Cached input** | ~$0.15 | — | Repeated context is deeply discounted |
| **Standard** | $1.74 | $3.48 | List price as of May 2026 |
| **Promotional** | $0.44 | $0.87 | Launch discount (ended May 5, 2026) |

Any OpenAI-compatible provider works — the system is model-agnostic by design.

#### 2.6.1 Confidence-Based Routing

```
Request arrives
       ↓
Local Gemma 4 assesses: "Can I handle this confidently?"
       ├─ YES (99% of tasks) → Execute locally, free
       └─ NO (complex/high-stakes) → Route to frontier API
              ↓
           Frontier model reads the same SSSS memory vault
              ↓
           Result written to VFS → Gemma 4 learns from it
```

#### 2.6.2 Frontier Eval Loop

Using DeepSeek V4 Pro at standard rates (**$1.74/M input, $3.48/M output**), quality gates remain inexpensive. Costs scale linearly with whichever provider the user configures:

| Task | Tokens | Cost (Standard) |
|:---|:---|:---|
| Evaluate 1 self-built skill (~5K in + ~1K out) | ~6K | ~$0.012 |
| Quality-gate 10 skills/day | ~60K | ~$0.12 |
| Full daily eval suite (50 test cases) | ~100K | ~$0.20 |
| **Monthly total (aggressive usage)** | **~5M** | **~$12** |

The eval loop:
1. Gemma 4 builds a skill autonomously (free, ~50 inference calls)
2. Gemma 4 self-tests the skill (free, ~10 calls)
3. Skill + test results sent to frontier model for independent evaluation (~$0.012 at DeepSeek standard rates)
4. Frontier model returns corrections
5. Gemma 4 applies fixes, re-tests, re-submits
6. Once validated → skill promoted to `status: validated`

#### 2.6.3 The Self-Improvement Flywheel

```
Gemma 4 (free) builds skills, researches, maintains memory
       ↓
Frontier model (~$0.012/eval) validates and corrects
       ↓
Corrections written to SSSS memory vault
       ↓
Gemma 4 sees corrections as few-shot examples in future calls
       ↓
Gemma 4 gets better → needs fewer frontier calls
       ↓
Costs decrease over time while quality increases
```

#### 2.6.4 Model Portability

Because the SSSS vault is plain text, the system is never locked into any model:

- **Swap the local kernel** anytime — if a better model drops, change one line in the Ollama config. The memory vault doesn't care.
- **Swap the frontier tier** — point `frontier.yml` at any OpenAI-compatible endpoint. Your memory works identically regardless of which model reads it.
- **Every frontier call improves the local model** — responses are written to the VFS, becoming few-shot examples. The system learns from the frontier model without fine-tuning.

## 4. Deployment Architecture (The Sovereign Cloud)

### 4.1 Oracle Cloud Always Free — Risk Analysis

The system standardizes on a single deployment target: **Oracle Cloud Infrastructure Ampere A1 Flex VM (4 OCPUs, 24GB RAM, 200GB Block Storage)**.

#### 4.1.1 Why Oracle

| Factor | Assessment |
|:---|:---|
| **Cost** | $0/month — permanent Always Free tier, not a trial |
| **RAM** | 24GB — the only free tier offering sufficient RAM for a quantized 26B model |
| **Storage** | 200GB persistent block — survives reboots, sufficient for years of VFS data |
| **Uptime** | VM runs 24/7 (not serverless, no cold starts, no sleep-on-idle) |
| **Network** | 10TB/month egress — ample for API + MCP + UI traffic |
| **Architecture** | ARM (aarch64) — excellent llama.cpp optimization, power-efficient |

#### 4.1.2 Known Risks & Mitigations

| Risk | Severity | Mitigation |
|:---|:---|:---|
| **Idle Reclamation** | 🔴 High | Oracle reclaims Always Free VMs idle for 7 days (CPU, network, AND memory all <10% p95 — some documentation cites 20%). The continuous intelligence daemon (`dream.mjs`) naturally maintains >10% CPU utilization through inference loops, **directly preventing reclamation**. |
| **Capacity Constraints** | 🟡 Medium | Ampere A1 availability varies by region. High-demand regions frequently show "Out of host capacity" errors during provisioning. Mitigation: target low-demand regions (e.g., `us-ashburn-1`, `ap-osaka-1`). |
| **Account Termination** | 🟡 Medium | Oracle has historically terminated accounts flagged as abusive. Mitigation: upgrade to Pay-As-You-Go (PAYG) — you still pay $0 for Always Free resources, but PAYG accounts are exempt from idle reclamation and less likely to be flagged. |
| **Vendor Lock-in** | 🟢 Low | The system is fully portable — it's a Docker container with a POSIX filesystem. Can be migrated to any Linux VM (Hetzner, home server, Raspberry Pi 5 cluster) in minutes. |

#### 4.1.3 Provisioning Sequence

```bash
# User provisions the free VM, then runs:
npx total-recall deploy

# The CLI performs:
# 1. Detects ARM architecture (aarch64)
# 2. Installs Ollama (ARM-native binary)
# 3. Pulls TotalRecall-Gemma-SSSS GGUF weights (Q4_K_M, ~16GB download)
# 4. Pulls Kokoro-82M weights (~200MB download)
# 5. Initializes VFS directory structure (~/.agent/memory-vault/)
# 6. Starts the OS daemon (dream.mjs) via systemd
# 7. Starts the HTTP server (express) on port 443 with auto-TLS
# 8. Registers systemd watchdog for auto-restart on crash
```

**Target: Full deployment in under 10 minutes** (bottlenecked by the ~16GB model download).

## 6. SSSS Memory Architecture (The Point of Differentiation)

The **Structured Semantic Syntax System (SSSS)** is Total Recall's proprietary schema — invented for this project, fully owned, and freely evolvable without external governance or standards bodies. It is not just a file format — it is a **complete database replacement** where human-readable Markdown files with semantic YAML frontmatter constitute the entire state machine, knowledge graph, and automation engine.

Because SSSS is ours and entirely self-contained as plain text files, both you AND the system itself can evolve the schema. The kernel can autonomously create new primitive types, extend frontmatter fields, refactor workflow semantics, and migrate its own memory nodes — no external tooling, no migration framework, no downtime. The schema evolves with the intelligence that runs on it.

> **Why this matters:** Every competitor (MemGPT, Jan.ai, AnythingLLM) bolts memory onto an existing database or vector store. Total Recall's memory IS the filesystem. There is no impedance mismatch between how the AI thinks and how data is stored — the LLM reads and writes the same Markdown files a human would edit in any text editor.

### 6.1 Core Mandates

1. **No Relational Databases** — No Postgres, SQLite, Redis, or vector databases. The POSIX filesystem is the only storage layer.
2. **Markdown is Law** — If it exists in the memory system (an assistant, a workflow, a preference, a decision), it exists as a `.md` or `.yml` file.
3. **Semantic Frontmatter** — Every file contains YAML frontmatter defining its `type`, metadata, and behavioral properties. The kernel validates this on every read.

### 6.2 SSSS Primitive Types

| `type` | Purpose | Key Frontmatter Fields |
|:---|:---|:---|
| `memory` | **Knowledge graph nodes** — the core product | `slug`, `category`, `schema_version`, `status`, `importance`, `priority`, `modality` |
| `assistant` | System instructions + chat logs | `name`, `model`, `voice_id`, `description` |
| `workflow` | Automation pipelines with triggers | `triggers[]`, `needs[]`, `name` |
| `task` | Autonomous scheduler work items | `priority`, `category`, `target`, `estimated_calls`, `deadline`, `created_by`, `status`, `progress` |
| `rule` | Global configuration / branding / logic | `name` |

### 6.3 Memory Node Schema (v2)

All files in `.agent/memory-vault/**/*.md` must contain the following YAML frontmatter. This schema is validated by Zod at runtime (`vault.mjs`) — malformed writes are rejected immediately.

```yaml
---
# === Identity ===
type: memory
slug: descriptive-lowercase-slug        # globally unique, kebab-case, matches filename
category: patterns                      # invariants | preferences | anti-patterns | patterns | decisions | concepts | facts | lore
title: "Human-readable description"     # concise title for indexing and display
schema_version: 2

# === Lifecycle ===
status: active                          # active | draft | superseded | deprecated
created: 2026-05-01T14:30:00Z
updated: 2026-05-10T14:03:00Z
last_accessed: 2026-05-09T17:55:00Z

# === Weight & Enforcement ===
importance: 3                           # 1–5 (1=trivial, 5=critical invariant)
priority: normal                        # normal | high | absolute
confidence: 0.92                        # 0.00–1.00, adjusted by Dream Cycle
modality: must                          # must | must_not | should | should_not | descriptive | preference

# === Semantic Ontology (enables O(1) conflict detection) ===
subject: agent                          # who is constrained
predicate: use_pm2_reload               # what action
object: deployment                      # on what target
sentiment_polarity: directive_must       # directive_must | directive_must_not | descriptive | preference
sentiment_target: "deployment"           # noun phrase this rule constrains

# === Provenance (append-only) ===
source:
  type: chat                            # chat | manual | mined | import
  session_id: 7f3a2b1c
  agent: antigravity
  evidence_count: 3

# === Relationships ===
supersedes: []                          # slugs this node replaces
superseded_by: null                     # slug that replaces this node
contradicts: []                         # slugs flagged by conflict detector
tags: [deploy, ops, pm2, zero-downtime]
related: [no-downtime-policy]
routes_to_skills: []                    # written by surface.mjs router

# === Decay ===
decay:
  half_life_days: 180                   # after this many days, confidence auto-decrements
  access_count: 12                      # incremented on every read; informs promotion
---
```

**Category taxonomy:**
- `invariants` — Unchanging truths (e.g., "User's name is Greg"). Directory: `memory-vault/invariants/`
- `preferences` — User preferences that may evolve (e.g., "Prefers dark mode"). Directory: `memory-vault/preferences/`
- `anti-patterns` — "Never do X" behavioral rules. Directory: `memory-vault/anti-patterns/`
- `patterns` — Observed behavioral patterns (e.g., "User always commits before switching tasks"). Directory: `memory-vault/patterns/`
- `decisions` — Architectural or life decisions with rationale. Directory: `memory-vault/decisions/`
- `concepts` — Learned domain knowledge. Directory: `memory-vault/concepts/`
- `facts` — General factual knowledge. Directory: `memory-vault/facts/`
- `lore` — Historical context, backstory, narrative. Directory: `memory-vault/lore/`

**Modality enforcement:**
- `must` / `must_not` — Hard behavioral rules injected into every prompt
- `should` / `should_not` — Soft preferences, can be overridden by context
- `descriptive` — Informational, no behavioral weight
- `preference` — User preference, applied when relevant

**Absolute rules** (stored in `memory-vault/invariants/`) additionally carry:
```yaml
priority: absolute                      # only absolute rules compile into Tier 1
immutable: true                         # surface.mjs refuses to overwrite without --force
```

### 6.4 Three-Tier Memory Hierarchy

| Tier | Location | Purpose | Latency |
|:---|:---|:---|:---|
| **Tier 1: Hot Memory** | Injected into system prompt | Active behavioral rules, critical invariants (`priority: absolute`, `modality: must`) | 0ms (always in context) |
| **Tier 2: Progressive Disclosure** | SKILL.md files, indexed JSONL | Curated knowledge surfaced on semantic relevance to the current query | ~100ms (index lookup) |
| **Tier 3: Permanent Vault** | `.agent/memory-vault/` | Full knowledge graph, archived logs, historical decisions, superseded memories | ~500ms (file I/O) |

**Promotion and demotion:** The Dream Cycle daemon continuously evaluates memory nodes and promotes/demotes them between tiers based on access frequency, importance score, and recency. A `priority: normal` fact accessed 50 times in a week may be promoted to `priority: high` and surfaced in Tier 2.

### 6.5 Memory Self-Evolution

Because SSSS is pure text files, the kernel can **mutate its own memory** — a capability no database-backed system can match without complex migration logic:

1. **Self-Editing:** The kernel can `fs.writeFile` any memory node, rewriting its content or updating frontmatter fields (e.g., changing `status: active` to `status: superseded`)
2. **Memory Compression:** When conversation logs exceed context limits, the dream cycle summarizes the last N turns, writes the summary as a new `category: concepts` memory node, archives the raw log, and updates the index
3. **Pattern Recognition:** The kernel analyzes interaction logs to identify recurring patterns, then creates new `category: patterns` memory nodes that influence future behavior
4. **Conflict Resolution:** When two memory nodes contradict each other, the dream cycle flags the conflict, evaluates by `importance` score, and marks the losing node as `status: superseded` with a rationale
5. **Schema Migration:** When the schema version increments (v2 → v3), a migration workflow rewrites all memory node frontmatter in-place — no database migration tools required

### 6.6 Dream Cycle Algorithm

The Dream Cycle is a background coprocessor (`dream.mjs`) that runs on both file-change events and a nightly cron schedule (`0 3 * * *` UTC). It performs autonomous memory maintenance in three phases:

```
PHASE 1 — Light Sleep (Scan & Ingest):
  [Lock: dream]
  1. Read all .md files in .agent/memory-vault/ modified in last 24h
  2. Read all .agent/sessions/*.jsonl modified since last cycle
  3. Extract candidate observations → write to scratchpad as pending_nodes[]

PHASE 2 — REM (Pattern Recognition & Conflict Detection):
  [Retry: 2, Timeout: 300s, OnError: Phase 4]
  FOR each pending node:
    1. Run 2-layer conflict detection (see §6.7)
    2. IF collision → emit conflict record to .agent/memory-inbox/conflicts/
    3. ELSE compute dream_score = f(evidence_count, recency_days, importance)

  PHASE 2a — [Parallel] Promote:
    FOR nodes with dream_score ≥ 0.65:
      Set status = active, bump confidence += 0.05 (cap 0.99)
    FOR nodes not accessed in 90d AND importance < 3:
      Decay confidence -= 0.02
    FOR nodes with confidence < 0.10:
      Set status = deprecated

  PHASE 2b — [Parallel] Conflict Surfacing:
    Append conflicts to .agent/memory-inbox/conflicts/
    Block promotion of conflicting nodes

PHASE 3 — Deep Sleep (Recompile):
  [Lock: surface]
  1. Run surface.compileSurface() → rebuild indexes, FTS5, skill capsules
  2. Run surface.compileTier1Instructions() → rebuild INSTRUCTIONS.md
  3. Append execution summary to .agent/memory-derived/dream-report.jsonl

PHASE 4 — Recover (OnError target):
  Restore .agent/skills/ and indexes from .agent/.backups/<timestamp>/
  Append failure to dream-report.jsonl
```

### 6.7 Conflict Detection & Resolution

Conflicts between memory nodes are detected using a **2-layer algorithm** that combines deterministic ontology checks with fuzzy similarity matching:

**Layer 1 — O(1) Ontology Check:**
```
IF new.modality OPPOSITE existing.modality
   AND new.subject == existing.subject
   AND new.predicate == existing.predicate
   AND new.object == existing.object
THEN → conflict (certainty: 1.0)
```

**Layer 2 — Fuzzy Similarity (only if Layer 1 passes):**
```
jaccard  = |tokens(new) ∩ tokens(existing)| / |tokens(new) ∪ tokens(existing)|
cosine   = dot(trigram_vec(new), trigram_vec(existing))
combined = 0.5 * jaccard + 0.5 * cosine
flip     = sentiment_polarity(new) OPPOSITE sentiment_polarity(existing)
           AND jaccard(target_NP(new), target_NP(existing)) ≥ 0.5

IF combined ≥ 0.78 AND flip == true
THEN → conflict
```

**Resolution policy (human-in-the-loop):**
1. New rule written to `.agent/memory-inbox/pending/`
2. Conflict engine compares against all active vault rules
3. If no conflict → rule activated
4. If conflict → written to `.agent/memory-inbox/conflicts/`, status set to `draft`
5. Conflict surfaced to user for explicit resolution
6. CLI: `total-recall resolve --keep <slug>` or `--supersede <slug>`
7. Loser's status set to `superseded`, winner's `supersedes[]` updated

> **Critical invariant:** The system NEVER auto-resolves conflicts. Silent conflict resolution is the #1 cause of catastrophic agent failures (ConInStruct, AAAI 2026).

### 6.8 SSSS Workflow Semantics

Workflows are the automation layer that **serves the memory system** — they ingest data, transform it, and write it back to the vault. Workflow semantics are defined in §2.1.2.

### 6.9 Recursive SSSS Self-Improvement

Because SSSS is proprietary and self-contained as plain text, the system can improve **the schema itself** — not just the content within it. The kernel performs autonomous architectural evolution:

```
Level 0: Execute SSSS workflows (use the schema)
Level 1: Build skills and memory (content within the schema)
Level 2: Identify limitations in the schema itself
Level 3: Propose, test, and apply improvements TO the schema
Level 4: Improved schema makes Levels 0-1 work better → repeat
```

**How it works:**

1. **Friction Detection:** The dream cycle logs every workflow execution failure, ambiguous parse, or repeated correction. When a pattern emerges (e.g., "parallel steps frequently have race conditions"), it creates a schema improvement task.
2. **Proposal:** The kernel drafts a new primitive or frontmatter field (e.g., a `[Barrier: wait_all]` semantic to synchronize parallel branches).
3. **Testing:** The proposed improvement is tested against existing workflows in the sandbox. Does it reduce failures? Does it break anything?
4. **Validation:** The frontier model reviews the proposal for ~$0.01. "Is this a sound architectural change? Any edge cases?"
5. **Application:** If tests pass and the frontier model approves, the SSSS spec file is updated. All future workflows can use the new primitive.
6. **Migration:** Existing workflows are optionally rewritten to use the new primitive, measured for improvement.

**Examples of emergent schema evolution:**

| Friction Observed | Proposed Improvement | Result |
|:---|:---|:---|
| Parallel steps have race conditions | New `[Barrier: wait_all]` primitive | Workflows can synchronize branches |
| Memory nodes frequently conflict | New `conflict_resolution:` frontmatter field | Automated conflict handling |
| Workflows need iteration | New `[Loop: until {condition}, max: N]` semantic | Cleaner iterative workflows |
| A memory category is never referenced | Deprecate and merge into related category | Simpler, tighter schema |
| Error handling is verbose | New `[Fallback: step_name]` shorthand | More concise workflow definitions |

**Why this is safe:**
- All changes are human-readable Markdown — open any file and see exactly what changed
- Frontier model validates before applying (pennies per review)
- Git version control — every schema change is a commit, roll back in one command
- High-impact changes can require `requires_approval: true` for human sign-off
- Changes are incremental — one primitive at a time, tested, kept only if it improves performance

> **The result:** SSSS evolves under selection pressure from real usage. The system performs natural selection on its own architecture — trying mutations, keeping what works, discarding what doesn't. No external standards body, no backwards compatibility debt, no committee. The schema evolves at the speed of inference.

### 6.10 Skill Routing Algorithm (`surface.mjs`)

The routing engine determines which memory nodes are injected into which `SKILL.md` files. It uses a **hybrid BM25 + TF-IDF scoring algorithm** with a hard cap of **7 rules per skill** (to prevent recreating context rot locally):

```
FOR each active memory node in vault:
  1. Build routing_text = title + tags + first_240_chars(body)
  2. Query FTS5 BM25:   bm25_scores[skill] = -bm25(skill_fts, routing_text)
  3. Compute TF-IDF:    tfidf_scores[skill] = tfidf(routing_text, skill_corpus)
  4. Z-normalize both score arrays
  5. combined[skill] = 0.7 * z(bm25) + 0.3 * z(tfidf)
  6. Pick top-K skills where combined ≥ 0.35 (default K=3)
  7. Union with explicit routes_to_skills from frontmatter
  8. Append node slug to each matched skill's needs[] array

FOR each skill:
  1. Sort needs[] alphabetically
  2. Cap at 7 highest-scoring slugs
  3. Render <!-- BEGIN INJECTED MEMORY --> block
  4. Atomic write to SKILL.md (write → rename to prevent corruption)

FOR absolute rules only:
  1. Compile into INSTRUCTIONS.md
  2. Hard-fail if total exceeds 1,000 tokens
```

**Injected memory block format** (fenced HTML comments for IDE compatibility):
```markdown
<!-- BEGIN INJECTED MEMORY: do not edit by hand; rebuilt by total-recall surface -->
<!-- @route: hybrid-bm25-tfidf, generated_at: 2026-05-10T14:03:00Z -->

- **prefer-pm2-reload** (confidence 0.92, importance 4):
  Use `pm2 reload <app>` for zero-downtime restarts. Never `stop && start`.

<!-- END INJECTED MEMORY -->
```

## 7. Security Model

> **Context:** Total Recall runs on user-owned infrastructure (their Oracle VM, their account, their data). We are not operating a multi-tenant service. Security is about protecting the user's sovereign data from external threats and containing the blast radius of autonomous code execution.

### 7.1 Network Security

| Layer | Implementation |
|:---|:---|
| **TLS Termination** | Caddy reverse proxy with automatic Let's Encrypt certificate provisioning and renewal |
| **Firewall** | Only ports 443 (HTTPS) and 22 (SSH, key-only) open via OCI Security Lists. All other ports blocked |
| **Rate Limiting** | Token bucket rate limiter on `/v1/chat/completions` and MCP endpoints — prevents brute-force and abuse |

### 7.2 Authentication & Authorization

| Endpoint | Auth Method |
|:---|:---|
| **Dashboard** | Session-based auth with bcrypt password hash; optional TOTP 2FA |
| **API** | Bearer PAT via `Authorization` header. Tokens stored as bcrypt hashes in `~/.agent/config/auth.yml` |
| **MCP Gateway** | OAuth 2.1 with PKCE or Bearer PAT |
| **SSH** | Key-only (password auth disabled) |

### 7.3 Code Mode Sandbox Isolation

The Code Mode sandbox executes user-generated and AI-generated scripts. Containment is critical:

- **Filesystem:** Scoped to `~/.agent/` — no access to host system files, no `/etc`, no `/root`
- **Network:** Opt-in per script. Default: no outbound network. Scripts must declare `needs: [network]` to make HTTP requests
- **Process:** No `child_process.exec` on host. Scripts run in isolated Node.js worker threads with `--experimental-vm-modules`
- **Resources:** 60-second timeout, 512MB memory cap, CPU nice level +10
- **Credentials:** Injected via `{{secrets.*}}` at runtime, never written to disk in plaintext

### 7.4 Credential Management

- All secrets stored in `~/.agent/config/secrets.enc` encrypted with AES-256-GCM
- Master key derived from user password via Argon2id (memory-hard KDF)
- Secrets injected into Code Mode via environment variables at execution time, never persisted in script files or VFS markdown
- PAT rotation policy: tokens expire after 90 days by default, configurable

The export is a plain POSIX directory tree of Markdown files. It works on any machine with Node.js — no Oracle dependency, no vendor lock-in. The user's memory is fully portable.

### 10.3 SSSS Schema Versioning

When the schema version increments (e.g., v2 → v3):

1. A migration workflow scans all `.md` files in the vault
2. Transforms frontmatter fields in-place (add new fields, rename deprecated ones)
3. Validates every node post-migration
4. Commits a migration log to `~/.agent/logs/migrations/`
5. No external tooling required — it's just text file manipulation

## 13. Technical Risks & Open Questions

| # | Risk / Question | Status |
|:---|:---|:---|
| **R-1** | Memory-based in-context learning may not match LoRA fine-tuning quality for highly specialized behaviors. Mitigation: cloud-burst LoRA training as upgrade path (~$1–5/week). | 🟡 Needs validation |
| **R-2** | Q4_0 KV cache quantization may degrade output quality at the margins. Needs A/B testing against Q8_0 and FP16 baselines. | 🟡 Needs benchmarking |
| **R-3** | Oracle A1 capacity shortages may prevent initial VM provisioning in popular regions | 🟡 Document fallback regions |
| **R-4** | Practical KV cache on 24GB RAM limits usable context to ~32K–48K tokens with Q4_0 cache. Must validate this is sufficient for aggressive context filling. | 🟡 Needs benchmarking |
| **R-5** | Frontier eval tier depends on external API availability. If the configured provider goes offline, the system loses quality gates but continues operating locally at full capacity. Mitigation: model-agnostic BYOK routing — user can switch providers in one config change. | 🟢 Low risk |
| **R-6** | Filesystem-based memory at scale (>10K nodes) may degrade index rebuild time. May need to shard the vault directory structure. | 🟡 Needs load testing |
| **R-7** | Oracle Always Free account termination risk. Mitigation: PAYG upgrade + documented export/migration path. | 🟡 Documented |
| **R-8** | Recursive schema self-improvement could introduce regressions if not properly gated. Mitigation: all schema changes require frontier validation + git commit + optional human approval for high-impact changes. | 🟡 Mitigated |
| **R-9** | Proactive web search may retrieve inaccurate or outdated information. Mitigation: frontier eval loop cross-checks research accuracy; skills built from web data default to `status: draft` until validated. | 🟡 Mitigated |

## Appendix B: Competitive Landscape (2026)

| Platform | What It Does | Why Total Recall Wins |
|:---|:---|:---|
| **MemGPT / Letta** | Persistent memory management for LLMs via tiered memory + tool calls | Bolt-on memory over existing DBs. Total Recall's memory IS the filesystem — no impedance mismatch, no ORM, no migration tooling |
| **Open Interpreter** | Local LLM + code execution + tool use | No persistent memory architecture. Each session starts fresh. No SSSS schema, no dream cycle |
| **Jan.ai** | Local model runner + agentic UI | No structured memory system, no autonomous background loops, no self-evolution |
| **AnythingLLM** | Private RAG over local files | Vector-store dependent. No native workflow engine, no Code Mode sandbox, no autonomous skill engineering |
| **CrewAI / LangGraph** | Multi-agent orchestration frameworks | Orchestration without memory. Agents are stateless by default. No sovereign VFS |
| **Hermes Agent** | Deep developer control over agent stack | No standardized schema. No file-native memory hierarchy. Requires extensive configuration |
| **Vellum** | Persistent identity + tool integration | Cloud-dependent SaaS. Not self-hosted, not database-free, not sovereign |
